# 淘宝用户行为分析报告

> **1225 万条真实电商行为日志 · 从数据治理到因果推断的完整分析链路**
>
> 数据来源：阿里巴巴移动推荐算法竞赛训练集（天池，2014 年）
> 分析周期：2026.09
> 作者：周成 ｜ 大数据管理与应用 ｜ 2027 届

## 摘要

本报告基于 **12,256,906 条**淘宝用户行为日志（507 MB，2014-11-18 ~ 2014-12-18，含双十二大促），完成了一条完整的分析链路：

**数据质量诊断 → 分层数仓建模 → 指标体系设计 → 转化漏斗与同期群留存 → 用户分层与归因 → 商品质量分层 → 大促增量因果推断**

### 六个核心结论

| # | 结论 | 关键数据 |
|---|---|---|
| **1** | **双十二效应 100% 集中在 12-12 单日**，当天带来 **+2,455 名支付用户净增量**（+170.25%），且为真实净新增而非跨期替代 | 逐日净效应：12-10 −7.93%、12-11 −5.85%、12-12 **+174.11%**（均为相对上周同日） |
| **2** | **最大人群不是"低频用户"，而是"高频低转化用户"**，占 30.77% | 活跃 25.9 天但只买 7.9 次，对比核心用户活跃 27.9 天买 33.4 次 |
| **3** | **商品流量极度长尾**，C+D 类商品占 75.63%，消耗 58.6% 点击量但几乎不产出 | A 类点击→支付率 5.32% vs D 类 0.42%，**效率差 12.7 倍** |
| **4** | **转化漏斗必须用 UV 口径且不能做成单链** | PV 口径 2.97% vs UV 口径 86.14%（差 29 倍）；9.59% 的支付用户跳过加购 |
| **5** | **地理位置字段行级覆盖率 32%，但用户级覆盖率 81.9%** | 缺失值诊断必须同时看行级和主体级两个口径 |
| **6** | **本数据集不适合做流失预测**（诊断后主动跳过） | 65.8% 用户在最后一天仍活跃；基准准确率已达 96.12% |

## 二、技术架构

### 2.1 架构设计（OLAP/OLTP 分离）

```
  CSV (507.3 MB / 1225.7 万行)
          │
          ▼
 ┌──────────────────────────────────┐
 │  DuckDB  ·  OLAP 分析引擎          │   流式扫描 → 清洗 → 窗口函数 → 漏斗/留存/RFM/DID
 │  列式存储 / 向量化执行 / v1.5.5     │   产物：Parquet 列存（124.1 MB）+ 指标表
 └──────────────────────────────────┘
          │  仅将聚合结果写入
          ▼
 ┌──────────────────────────────────┐
 │  MySQL 8.0  ·  OLTP 结果仓储      │   存储指标表，供 BI / 看板消费
 └──────────────────────────────────┘
          │
          ▼
      可视化 / 分析报告
```

**设计理由**：

| 问题 | 回答 |
|---|---|
| **为什么不用 pandas 直接读？** | 1225 万行 CSV 用 pandas 加载需 **1.5 GB+ 内存**，且 `apply` 逐行解析时间字段极慢。DuckDB 为**流式扫描**，内存占用恒定 |
| **为什么不把原始数据灌 MySQL？** | MySQL 是行存 OLTP 数据库，千万级批量导入需数十分钟至数小时，索引维护成本高。**故 DuckDB 负责「算」，MySQL 负责「存」** |
| **为什么落 Parquet？** | 507.3 MB → **124.1 MB（压缩率 24.5%）**，且列式存储让后续查询**只读需要的列** |

### 2.2 数仓分层

| 层 | 职责 | 实现 |
|---|---|---|
| **ODS** | 原始数据层 | 原始 CSV |
| **DWS** | 汇总数据层 | `dws_user_daily`（202,324 行）、`dws_user_profile`（10,000 行） |
| **ADS** | 应用数据层 | 漏斗、留存、RFM、商品质量、用户分层、DID 等 8 张表 |

### 2.3 技术栈

| 类别 | 技术 |
|---|---|
| **分析引擎** | DuckDB 1.5.5（列存 / 流式扫描 / 窗口函数 / QUALIFY） |
| **结果仓储** | MySQL 8.0.42 |
| **语言与库** | Python 3.12（pandas / scipy / statsmodels） |
| **工程实践** | venv 环境隔离 / requirements 版本锁定 / Git 版本管理 / 运行日志与异常留痕 |

## 三、分析过程与核心发现

### 3.1 数据质量诊断（P1）

**诊断七个维度：表结构、规模、时间边界、行为分布、缺失值、重复记录、值合理性。**

#### 发现 1｜重复记录的性质判定（**方法论案例**）

初步检测发现 **49.31%** 的记录满足「同一用户 + 同一商品 + 同一行为 + 同一小时」。

**我最初的判断是"日志重复上报"（数据质量问题），建议去重。** 但通过四项统计检验推翻了：

| 检验 | 结果 | 判定 |
|---|---|---|
| 重复次数分布 | 2 次占 63.58%，单调递减，**最大仅 22 次** | 不符合系统故障的长尾形态 |
| 用户分布 | **99.69%（9,969/10,000）** 的用户有重复 | 不是集中在少数用户 |
| **按小时分布** | **24 小时重复率锁在 47%~50%** |  **决定性证据** |
| 内容差异 | 差异 100% 来自 `user_geohash` | 位置字段稀疏记录 |

**结论**：**重复记录是真实用户行为（深度回访），不做去重。**

> **决定性逻辑**：如果是日志 bug，必有触发条件；最可能是流量压力，那重复率应在高峰时段更高。**但 24 小时的重复率完全不受时段影响（03 点 47.35% vs 09 点 49.79%）—— 一个系统 bug 不会这么"守规矩"。**

#### 发现 2｜地理位置字段的双口径覆盖率（**方法论案例**）

| 口径 | 计算 | 结果 |
|---|---|---|
| **行级覆盖率** | 3,922,082 / 12,256,906 | **31.999%** |
| **用户级覆盖率** | 8,190 / 10,000 | **81.9%** |

**差 2.5 倍，原因**：日志**稀疏记录**位置 —— 用户不是每次行为都上报位置，但只要有**一次**上报，这个人就能被定位。

**结论**：
- ✅ **用户级地域分析可用**（81.9%）
- ❌ **事件级地域分析不可用** —— 另有稳定性检查显示 **33.7% 的多行组合存在同小时多地理编码**（可能是 GPS 漂移或基站切换）

#### 发现 3｜数据自相矛盾的处理

两个去重口径给出不同结果：`GROUP BY 4 列` = 6,213,379 行，`DISTINCT 全字段` = 8,164,040 行，**差 1,950,661 行**。

**我没有挑一个信，而是做了交叉验证**，最终定位差异 **100% 来自 `user_geohash`**（地理不同的组合数 1,296,389，类目不同的组合数 0）。

**结论**：`user_geohash` 不能作为去重键 —— 同一批日志的两次上报可能一次带位置、一次不带。

#### P1 数据质量汇总

| 检查项 | 结果 |
|---|---|
| 核心字段缺失 | user_id / item_id / behavior_type / item_category / time **全部 0.000%** |
| 唯一缺失字段 | `user_geohash` 68.001% |
| 值越界 | 行为编码越界 0 / ID 非正 0 / 时间越界 0 |
| Parquet 压缩 | 507.3 MB → 124.1 MB（**24.5%**） |
| 全流程耗时 | **10.1 秒** |

### 3.2 指标体系建设（P2）

#### 指标口径字典（**核心产出**）

建立了 **4 层指标体系**（获取 / 激活 / 留存 / 变现），并为每个指标显式定义分子分母。

**关键设计：付费率的双口径**

```
pay_rate_dau   = buy_uv / uv         ← 平台整体变现效率
pay_rate_click = buy_uv / click_uv   ← 有意向用户的转化效率
```

**为什么给两个**：付费率低，可能是**流量质量差**，也可能是**路径设计差**。**只给一个口径，无法区分是哪个问题。**

#### 发现 1｜转化漏斗必须用 UV 且不能做成单链

**PV 口径 vs UV 口径的差异**：

| 口径 | 点击 | 加购 | 转化率 |
|---|---|---|---|
| **PV（事件数）** | 11,550,581 次 | 343,564 次 | **2.97%** |
| **UV（去重用户）** | 10,000 人 | 8,614 人 | **86.14%** |

**同一业务事实，两个口径差 29 倍。**

**为什么**：PV 衡量"**事件之间的比例**"，UV 衡量"**人之间的比例**"。**而运营策略是针对人制定的。**

**单链漏斗的失败**（我自己的设计错误）：

第一版漏斗算出 **103.16%** 的转化率 —— **转化率超过 100%，说明结构假设错了。**

**路径交叉分析给出答案**：

| 路径 | 用户数 | 占支付用户 |
|---|---|---|
| B-加购+收藏后支付 | 5,739 | 64.58% |
| C-仅加购后支付 | 2,295 | 25.83% |
| D-仅收藏后支付 | 517 | 5.82% |
| **E-直接支付（未加购未收藏）** | **335** | **3.77%** |

**852 人（9.59%）跳过了加购** —— **单链漏斗会完全漏掉这部分人。**

**修正**：改为**各环节占大盘百分比 + 支付用户路径拆解**的双结构。

#### 发现 2｜摩擦成本必须区分原始点击与有效点击

| 口径 | 计算 | 结果 |
|---|---|---|
| **原始点击** | 11,550,581 ÷ 120,205 | **96.1 次点击/支付** |
| **有效点击**（去重 用户×商品） | 3,996,500 ÷ 120,205 | **38.9 次点击/支付** |
| **重复点击占比** | — | **59.5%** |

**结论**：用户完成一次支付，平均需要**探索约 39 个不同的商品**。

> **数据要保留（重复点击是真实行为），但指标要分口径（算效率时必须用有效点击）。**

#### 发现 3｜商品质量分层（**可直接交付选品团队**）

按**商品级点击→加购率**分层（抽样 550 个点击≥50 的商品）：

| 商品分层 | 商品数 | 占比 | 总点击 | 总加购 | 总支付 | 点击→加购率 |
|---|---|---|---|---|---|---|
| **A-高意向** | 11 | **2.00%** | 3,419 | 331 | **182** | **9.68%** |
| B-中等意向 | 123 | 22.36% | 33,949 | 1,732 | 809 | 5.10% |
| **C-低意向** | 210 | 38.18% | 60,539 | 1,756 | 775 | 2.90% |
| **D-需优化** | 206 | **37.45%** | **63,159** | **623** | **265** | **0.99%** |

**三个可直接汇报的结论**：

| # | 结论 |
|---|---|
| **1** | **C + D 类商品占 75.63%，消耗 58.6% 的点击量** |
| **2** | **D 类商品是"流量黑洞"**：206 个商品 63,159 次点击，只换来 623 次加购、265 次支付（点击→加购率 **0.99%**） |
| **3** | **A 类效率是 D 类的 12.7 倍**（点击→支付率 5.32% vs 0.42%） |

#### 发现 4｜同期群留存矩阵

**原项目用"31 天累计复购率 87%"冒充留存率**，有三个问题：
① 不是留存，是累计复购；② 分母是"有购买行为的人"这个**条件子集**；③ 没有时间维度。

**修正为同期群（Cohort）留存** —— 按用户首次活跃日分组，追踪后续第 N 天回访：

| 队列 | D1 留存 | D7 留存 | 队列规模 |
|---|---|---|---|
| 2014-11-18 | **80.99%** | **75.55%** | 6,343 |
| 2014-11-19 | 61.03% | 58.14% | 1,283 |
| 2014-11-20 | 55.45% | 55.64% | 550 |
| ... | ... | ... | 样本 <100 标"不解读" |

**局限声明**：样本是高活跃子集，**留存率绝对值不具代表性，方法论才是核心产出**。

### 3.3 用户分层与归因（P3）

#### 分层设计（修正版）

按「活跃度 × 转化率」二维交叉，共 8 类：

| 用户分层 | 用户数 | 占比 | 平均最近间隔 | 平均活跃天数 | **平均购买次数** |
|---|---|---|---|---|---|
| **高频低转化用户** | **3,077** | **30.77%** | 0.3 天 | **25.9** | **7.9** |
| 中频低转化用户 | 2,897 | 28.97% | 1.3 天 | 14.7 | 5.2 |
| **核心价值用户** | 2,183 | 21.83% | 0.1 天 | **27.9** | **33.4** |
| **未购买用户** | **1,114** | 11.14% | 3.8 天 | 11.0 | **0.0** |
| 中频高转化用户 | 249 | 2.49% | 0.9 天 | 16.7 | 24.7 |
| 新客 | 256 | 2.56% | 1.0 天 | 5.2 | 3.3 |
| 流失预警用户 | 151 | 1.51% | 10.2 天 | 8.2 | 3.5 |
| 已流失用户 | 73 | 0.73% | 19.3 天 | 4.9 | 3.1 |

#### 核心商业发现：**最大人群不是"低频用户"**

| 对比 | 核心价值用户 | 高频低转化用户 | **差异** |
|---|---|---|---|
| 平均活跃天数 | 27.9 天 | 25.9 天 | **几乎一样（0.93 倍）** |
| 平均点击 | 2,421 | 1,379 | 0.57 倍 |
| **平均加购** | 90.7 | 29.0 | **0.32 倍** ← ★ **断崖** |
| 平均支付 | 33.4 | 7.9 | 0.24 倍 |
| 加购转支付率 | 36.81% | 27.31% | 0.74 倍 |

**倍数差定位法揭示了病灶位置**：

```
活跃天数  0.93  ← 不是"不活跃"的问题
点击      0.57  ← 浏览广度不够
加购      0.32  ← ★ 最大断崖在这里
支付      0.24
```

**→ 病灶：**「看了之后加购的太少」，而不是「他们不来」或「他们不看」。

#### 四个假设的验证结果

| 假设 | 结论 | 关键证据 |
|---|---|---|
| **H1** 浏览分散、无聚焦 | ❌ **否定** | 核心用户浏览品类**更多**（160.8 vs 109.0），且两组"行为数÷品类数"比例接近（16.2 vs 13.2）→ **浏览模式无本质差异** |
| **H2** 购买集中在大促 | ❌ **否定** | 所有活跃人群大促购买占比 **18%~19.4%**，无差异（基准 9.68%） |
| **H3** 有意向但犹豫 | ✅ **成立** | 加购转支付率 27.31% vs 36.81%（低 26%） |
| **H4** 根本没意向 | ✅ **成立** | 加购率 2.10% vs 3.75%（低 44%） |

#### 一个反直觉发现：**"加购转支付率"和"用户价值"是反着的**

| 分层 | 加购转支付率 | 用户价值 |
|---|---|---|
| 新客 | **94.91%** | 低 |
| 已流失用户 | 87.45% | 低 |
| 中频高转化用户 | 57.78% | 中 |
| **核心价值用户** | **36.81%** | **最高** |
| 高频低转化用户 | 27.31% | 高 |

**解释**：
- **新客是"目标明确型"** —— 搜到就加购、加购就下单，加购是"已经决定买"的动作
- **重度用户是"购物车管理型"** —— 把加购当收藏夹，加一堆慢慢挑

> **所以核心价值用户之所以是核心，不是转化率高，而是行为量是别人的 3 倍。用户价值 = 行为量 × 转化率，行为量可以弥补转化率的劣势。**

#### 未购买用户（1,114 人）的拆解

| 子类 | 人数 | 占比 |
|---|---|---|
| **加购过但没买** | **580** | **52.1%** ← 可挽回 |
| 从未加购也未收藏 | 341 | 30.6% |
| 仅收藏过 | 193 | 17.3% |

**业务含义**：**如果直接对 1,114 人全量投放优惠券，会有 30% 的预算浪费在不可能转化的人身上。**

### 3.4 大促增量因果推断（P4）

#### 方法设计（五步递进）

| 步 | 方法 | 解决什么 |
|---|---|---|
| 1 | 描述性对照 | 摊开现象，**明确标注不能解读为因果** |
| 2 | 平行趋势观察 | 按星期几对齐日序列 |
| 3 | **双重差分（DID）** | 构造反事实，剔除自然变化 |
| 4 | **同星期几配对** | 消除周末效应 |
| 5 | **事件研究法 + 窗口敏感性** | 暴露时间位移，验证稳健性 |

#### 核心结果：效应 100% 集中在单日

**大促 3 天逐日净效应（同星期几配对）**：

| 日期 | 星期 | 实际支付用户 | 同星期几对照 | **净增量** | **相对变化** |
|---|---|---|---|---|---|
| 12-10 | 周三 | 1,442 | 1,566 | **−124** | **−7.93%** |
| 12-11 | 周四 | 1,449 | 1,539 | **−90** | **−5.85%** |
| **12-12** | **周五** | **3,897** | **1,422** | **+2,475** | **+174.11%** |

**结论**：**"大促 3 天"这个概念是错的 —— 前两天不是"大促"，是"抑制期"。**
**用 3 天平均算净增量 = +754 人（+49.95%），严重低估了真实效应。**

#### 效应分解：两股力量的抵消结构

| 时期 | 天数 | 实际累计 | 基线累计 | **累计差额** |
|---|---|---|---|---|
| **A-消费前移期(12-02~05)** | 4 | 6,360 | 6,019 | **+341** |
| **B-抑制期(12-06~11)** | 6 | 8,726 | 9,047 | **−321** |
| **C-大促当天(12-12)** | 1 | 3,897 | 1,442 | **+2,455** |
| **D-大促后(12-13~18)** | 6 | 9,454 | 9,047 | **+408** |
| **全窗口净效应** | 17 | — | — | **+2,883** |

**关键结构**：

```
消费前移期  +341   ← 用户提前买
抑制期      −321   ← 用户憋着不买
             ────
两股力量净和  +20   ≈ 0   ← 几乎完全抵消
```

**这一抵消关系证明了关键判断**：**大促前的两股力量是"零和"的（需求在时间上换位，总量不变），所以 12-12 的 +2,455 是【真实净新增需求】，而不是把后面的购买提前。**

#### 稳健性：四重验证

| 检验 | 结果 | 判定 |
|---|---|---|
| **三口径对比** | 2,455 / 2,404 / 2,393 | ✅ 差异 **< 3%** |
| **三窗口敏感性** | +193.01% / +165.55% / +170.25% | ✅ 方向一致 |
| **逐日序列** | 周五：1,330 → 1,442 → 1,493 → **3,897** | ✅ 断崖式跳升 |
| **全窗口净效应** | **+2,883 ≫ 0** | ✅ 非纯粹跨期替代 |

### 3.5 流失预警可行性诊断（P5，**主动跳过**）

**项目原计划 P5 交付流失预警模型，但动手前的可行性诊断否决了这个模块。**

| 诊断 | 结果 | 判定 |
|---|---|---|
| **窗口截断效应** | **65.8% 的用户在最后一天（12-18）仍活跃** | ❌ 严重 |
| **真实衰减用户** | 完全停止 131 + 大幅衰减 409 = **540 人（5.4%）** |  偏少 |
| **标签平衡** | 流失率 **3.88%**，"全预测不流失"基准准确率 **96.12%** | ❌ 极端不平衡 |
| **规律复杂度** | 见下表 | ❌ **过于简单** |

**决定性证据 —— 活跃天数 → 流失率的单调关系**：

| 特征窗口活跃天数 | 用户数 | 流失数 | **流失率** |
|---|---|---|---|
| **1 天** | 697 | 140 | **20.09%** |
| 2 天 | 816 | 85 | 10.42% |
| 3 天 | 861 | 45 | 5.23% |
| 4 天 | 1,097 | 43 | 3.92% |
| 5 天 | 1,378 | 24 | 1.74% |
| 6 天 | 1,607 | 13 | 0.81% |
| **7 天** | 2,659 | 4 | **0.15%** |

> **流失率从 20.09% 到 0.15%，跨了 134 倍，完美单调。**
> **也就是说，一个能用一句话说完的规律（"本周来得少的人，下周大概率不来"），不需要机器学习模型。**

## 六、方法论沉淀

本报告的产出不止于结论，更在于**可复用的分析方法**：

| # | 方法 | 应用场景 |
|---|---|---|
| **1** | **多口径 + 窗口敏感性检验** | 对抗"挑基线支持结论"的倾向 —— 当一个结论只在特定口径下成立时，它不稳健 |
| **2** | **行级 vs 主体级双口径覆盖率** | 缺失值诊断必须同时看两个口径，否则会错误弃用可用维度 |
| **3** | **倍数差定位法** | 通过逐环节的倍数对比，定位漏斗中的"断崖"位置 |
| **4** | **假设检验 + 统计学证据链** | 判定数据性质（如"重复记录是真实行为"）时，设计能判定的实验而不是靠直觉 |
| **5** | **构造反事实（DID + 同星期几配对）** | 没有随机对照组时评估干预效果 |
| **6** | **效应分解（前移 / 抑制 / 净增）** | 区分"时间位移"与"真实净增" |
| **7** | **可行性诊断前置** | 在投入建模前验证数据是否支持任务 |

### 三次自我纠错（**方法论精华**）

| # | 错误 | 根因 | 对抗方法 |
|---|---|---|---|
| **1** | DID 处理组定义自相矛盾（结果 NaN） | 把"时间块"当成处理单元 | 认清处理单元是"那一天的哪些用户" |
| **2** | "抑制效应"误判（有→无） | 只用一个基线，且在挑支持结论的 | 多口径 + 窗口敏感性 |
| **3** | "周增长趋势"是伪趋势（R²=0.16） | 只看两个相邻点就外推 | 输出完整序列 |

> **三次的共同根因：从局部数据外推整体结论。**
>
> **沉淀原则**：**当你需要"挑"一个基线或"挑"一段数据来支持结论时，说明结论本身不稳健。正确的做法是同时跑多个口径，看结论会不会变。**
