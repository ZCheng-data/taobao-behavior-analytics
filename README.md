## 一、核心结论

> 完整的推导过程见 [`docs/完整项目分析报告.md`](docs/完整项目分析报告.md)

### 1️⃣ 漏斗口径选错，结论会差 29 倍

点击 → 加购 这一步：

| 口径 | 算法 | 结果 |
|---|---|---|
| PV（事件数） | 加购事件数 ÷ 点击事件数 | **2.97%** |
| **UV（去重用户）** | 加购人数 ÷ 点击人数 | **86.14%** |

差 29 倍。原因：同一批人反复点击同一批商品，PV 口径衡量的是"事件之间的比例"，而运营策略是针对**人**制定的。
**本项目所有漏斗一律采用 UV 口径。**

### 2️⃣ 单链漏斗是错的：9.59% 的支付用户跳过了加购

全周期有支付的用户 **8,886 人**，反而**多于**有加购的 8,614 人 —— 两者不是包含关系。

按支付用户的实际路径拆解（分母 = 8,886 名支付用户）：

| 用户路径 | 占比 | 人数 |
|---|---|---|
| 加购 + 收藏 | 64.58% | 5,739 |
| 仅加购 | 25.83% | 2,295 |
| 仅收藏后支付（跳过加购） | 5.82% | 517 |
| **完全直接支付（未加购未收藏）** | **3.77%** | **335** |

**跳过加购的支付用户合计 852 人（9.59%）** —— 刚性三步漏斗会完全看不见这部分人，并算出 >100% 的荒谬转化率。

### 3️⃣ 49.3% 的"重复记录"是真实行为，不做去重

四列完全重复的记录占 **49.31%**，最初判断为日志重复上报。但四项统计检验推翻了它：

| 检验 | 结果 | 判定 |
|---|---|---|
| 重复次数分布 | 2 次占 63.58%，单调递减，**最大仅 22 次** | 不符合系统故障的长尾形态 |
| 用户分布 | **99.69%（9,969/10,000）** 用户有重复 | 不是集中在少数用户 |
| **按小时分布** | **24 小时重复率锁定在 47%~50%** | ⭐ 决定性证据 |
| 内容差异 | 差异 100% 来自 `user_geohash` | 位置字段稀疏记录 |

**决定性逻辑**：若是日志 bug 必有触发条件（最可能是流量压力）。但凌晨 3 点（47.35%）与早 9 点（49.79%）的重复率几乎相同 —— 系统故障不会这么"守规矩"。

### 4️⃣ 字段覆盖率有"行级 / 用户级"两个口径，差 2.5 倍

| 口径 | 计算 | 结果 |
|---|---|---|
| 行级覆盖率 | 3,922,082 / 12,256,906 | **31.999%** |
| **用户级覆盖率** | 8,190 / 10,000 | **81.9%** |

只按行级判断会错误弃用一个可用维度。**但用户级可用 ≠ 事件级可用**：另有 33.7% 的多行组合存在同小时多地理编码，因此地域分析只做到用户维度。

### 5️⃣ 高频低转化用户是最大人群，断崖在"加购"这一步

高频低转化用户 **3,077 人（30.77%）**，是占比最高的人群；核心价值用户 2,183 人（21.83%）。

倍数差定位法锁定病灶位置：

```
活跃天数  0.93  ← 不是"不活跃"的问题
点击      0.57  ← 浏览广度不够
加购      0.32  ← ★ 最大断崖在这里
支付      0.24
```

**→ 病灶是「看了之后加购的太少」，而不是「他们不来」或「他们不看」。**
另有 1,114 名零购买用户中，**52.1% 其实加购过商品** —— 属于"有意向、未成交"，可直接定向触达。

### 6️⃣ 双十二当天净增 +2,455 名支付用户

用**同星期几配对 + 双重差分**构造反事实基线，大促三天呈现清晰的"先抑后爆"：

| 日期 | 相对上周同日 |
|---|---|
| 12-10（大促前两天） | **−7.93%** |
| 12-11（大促前一天） | **−5.85%** |
| **12-12（大促当天）** | **+174.11%** |

**三口径交叉验证**（换三种反事实基线）：净增 **2,455 / 2,404 / 2,393** 名支付用户，差异 < 3%。
**三窗口敏感性**：+193.01% / +165.55% / +170.25%，方向完全一致 —— **结论不依赖基线或窗口的选取**。

效应分解：消费前移 +341 ／ 大促前抑制 −321 ／ 当日净增 +2,455 ／ 大促后回落 +408。
其中前两项几乎完全抵消（净和 +20 ≈ 0），**证明 12-12 的增量是真实净新增，而不是把大促前后的购买提前**。

## 二、数据说明

| 项目 | 说明 |
|---|---|
| **来源** | 阿里巴巴「移动推荐算法」竞赛训练集（天池，2014 年） |
| **规模** | 12,256,906 行 ／ 507.3 MB |
| **时间跨度** | 2014-11-18 ~ 2014-12-18（31 天，含双十二大促 12-10~12-12） |
| **用户/商品/类目** | 10,000 用户 ／ 2,876,947 商品 ／ 8,916 类目 |

### 字段字典

| 字段 | 类型 | 含义 |
|---|---|---|
| `user_id` | int | 用户 ID（脱敏编号） |
| `item_id` | int | 商品 ID（脱敏） |
| `behavior_type` | int | 行为类型：**1=点击 2=收藏 3=加购 4=支付** |
| `user_geohash` | string | 用户地理位置（Geohash 编码），**大面积缺失** |
| `item_category` | int | 商品类目 ID |
| `time` | string | 行为发生时间，格式 `YYYY-MM-DD HH`（**精度只到小时**） |

### ⚠️ 三条数据边界（约束结论适用范围）

1. **时间精度只到小时** → 无法做行业标准的「30 分钟不活跃即新会话」切分，本项目采用**小时级近似会话**，会低估多会话用户比例
2. **无价格字段** → 所有指标均为**行为指标**（人数、转化率、留存率、复购率），**不涉及 GMV / 客单价 / ARPU / ROI**
3. **用户数为整数 10,000** → 这是按用户维度抽样的**高活跃样本**，留存率的绝对值不具代表性；本项目的产出是**方法论与场景结论**，不代表淘宝全量

> 📌 数据文件未纳入版本库（体积原因）。请从天池获取后放置于 `data/raw/train_user.csv`。

## 三、技术架构

```
 CSV (507 MB / 1225 万行)
        │
        ▼
 ┌─────────────────────────────┐
 │   DuckDB  ·  OLAP 分析引擎   │   流式扫描 → 清洗 → 数仓分层 → 窗口函数
 │   列式存储 / 向量化执行       │   产物：Parquet 列存 + 汇总表
 └─────────────────────────────┘
        │  仅将聚合结果写入
        ▼
 ┌─────────────────────────────┐
 │   MySQL 8.0  ·  OLTP 仓储    │   存储聚合后的指标表，供 BI 消费
 └─────────────────────────────┘
        │
        ▼
   Excel 结果表（reports/tables）
```

**为什么不全用 MySQL？**
1225 万行原始日志用 MySQL 行存批量导入很慢，索引维护成本也高。故采用 **OLAP（DuckDB 计算）+ OLTP（MySQL 存结果）分离**架构，只把聚合后的指标表落到 MySQL。

**为什么不用 pandas 直接读？**
12M 行 CSV 用 pandas 加载需 1.5GB+ 内存，逐行解析时间字段极慢。DuckDB 为流式扫描，内存占用恒定。清洗后转 Parquet 列存，507.3 MB → 124.1 MB，压缩率 **24.5%**。

### 数仓分层

| 层 | 表 | 说明 |
|---|---|---|
| **ODS** | `ods_user_behavior` | 原始日志直接落地，不改一行 |
| **DWD** | `dwd_user_behavior` | 清洗 + 派生字段 `dt / hr / ts / is_buy` |
| **DWS** | `dws_user_daily`、`dws_user_profile` | 用户日粒度指标、用户画像 |
| **ADS** | `ads_funnel`、`ads_path_breakdown`、`ads_retention`、`ads_rfm`、`ads_item_quality`、`ads_repeat_click` | 面向应用的结果表 |

## 六、分析方法说明

| 分析 | 方法 | 解决的问题 |
|---|---|---|
| **数据质量诊断** | 缺失率 / 越界值 / 重复模式 / 双口径覆盖率 | 数据能不能用？边界在哪？ |
| **转化漏斗** | 路径互斥分类 + `COUNT(DISTINCT user_id)` UV 口径 | 用户在哪一步流失最多？ |
| **同期群留存** | Cohort 矩阵（按首次活跃日分组） | 留存是变好还是变差？ |
| **用户分层** | 活跃度 × 转化率二维交叉 + 固定业务阈值 | 哪些人群值得投入资源？ |
| **大促增量** | 双重差分（DID）+ 同星期几配对 + 事件研究法 + 窗口敏感性 | 双十二到底带来多少**净增量**？ |
| **摩擦成本** | 原始点击 vs 去重后的"用户×商品"有效点击 | 从点击到成交的真实阻力有多大？ |

### 为什么没有做流失预警模型

原计划 P5 交付 LightGBM 流失预警模型，但**动手前的可行性诊断否决了它**：

| 诊断 | 结果 | 判定 |
|---|---|---|
| 窗口截断效应 | **65.8% 用户在最后一天（12-18）仍活跃** | ❌ 严重 |
| 标签平衡 | "全预测不流失"基准准确率 **96.12%** | ❌ 极端不平衡 |
| 规律复杂度 | 活跃天数 → 流失率 **20.09% → 0.15%，跨 134 倍且完美单调** | ❌ 过于简单 |

活跃天数与留存几乎一一对应，任何模型都只能复现这条规则，边际增益有限。**详见 [`docs/P5可行性诊断.md`](docs/P5可行性诊断.md)**。
